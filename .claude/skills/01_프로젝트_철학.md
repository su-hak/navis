# 01. 프로젝트 철학 및 핵심 원칙

> **목적**: 프로젝트 개발 시 일관되게 적용할 핵심 원칙과 철학

---

## 🏛️ 4대 핵심 철학

### 1. 실전 중심주의 (Production-First)
> "테스트는 실제 환경을 반영해야 한다"

**원칙**:
- ❌ **Mock 데이터 절대 금지** → 모든 테스트는 실제 DB 연결
- ✅ E2E 테스트에서도 실제 DB 사용
- ✅ 테스트 후 데이터 정리

**이유**: Mock은 실제 환경에서 발생하는 문제를 숨김

**실천 예시**:
```typescript
// ❌ 나쁜 예: Mock Repository 사용
const mockUserRepository = {
  findOne: jest.fn().mockResolvedValue({ id: '123' })
};

// ✅ 좋은 예: 실제 DB 연결
beforeEach(async () => {
  const moduleFixture = await Test.createTestingModule({
    imports: [AppModule], // 실제 DB 설정 포함
  }).compile();
  app = moduleFixture.createNestApplication();
  await app.init();
});
```

---

### 2. 일관성 우선주의 (Consistency-First)
> "비슷한 기능은 비슷한 구조로"

**원칙**:
- ✅ 구독/광고/사용자 시스템은 모든 프로젝트에서 동일한 패턴
- ✅ Skills 구조를 그대로 복사해서 사용
- ✅ 파일 이름, 디렉토리 구조 통일

**이유**: 새 프로젝트 시작 시 빠른 개발, 유지보수 용이

**실천 예시**:
```
모든 프로젝트에서 동일한 구조:
src/
├── auth/
│   ├── auth.module.ts
│   ├── auth.controller.ts
│   ├── auth.service.ts
│   ├── guards/
│   └── strategies/
├── users/
└── subscription/
```

---

### 3. 근본적 해결주의 (Root-Cause-First)
> "임시방편은 기술 부채를 만든다"

**원칙**:
- ❌ **파일 제거는 마지막 수단** → 반드시 허락받기
- ✅ 문제의 근본 원인을 찾아서 해결
- ✅ 임시 해결책 금지

**이유**: 제거는 쉽지만, 나중에 왜 그 파일이 있었는지 알 수 없음

**실천 예시**:
```typescript
// ❌ 나쁜 예: 에러 발생 → 코드 주석 처리
// const result = await this.someService.doSomething();

// ✅ 좋은 예: 에러 원인 파악 → 근본적 수정
try {
  const result = await this.someService.doSomething();
} catch (error) {
  this.logger.error('doSomething 실패:', error);
  throw new InternalServerErrorException('처리 중 오류 발생');
}
```

### 4. 투명성 원칙 (Transparency)
> "모든 변경사항은 추적 가능해야 한다"

**원칙**:
- ✅ 자동 커밋, 절대 푸시 금지
- ✅ 커밋 메시지는 반드시 한글
- ✅ Co-Authored-By 태그로 AI 작업 명시

**이유**: 팀원이 변경사항을 쉽게 이해 가능

## 🔄 Git Workflow

### 커밋 규칙

```bash
# 자동 커밋 (절대 푸시 금지)
git add .
git commit -m "구독 시스템 구현 완료

- User 엔티티에 구독 필드 추가
- Payment 엔티티 생성
- 정기 결제 스케줄러 구현

Co-Authored-By: Claude Sonnet 4.5 <noreply@anthropic.com>"
```

### 커밋 메시지 컨벤션

| 접두사 | 설명 | 예시 |
|--------|------|------|
| feat | 새 기능 추가 | feat: 구독 시스템 추가 |
| fix | 버그 수정 | fix: 로그인 토큰 만료 오류 수정 |
| refactor | 코드 리팩토링 | refactor: UserService 코드 정리 |
| docs | 문서 수정 | docs: README 업데이트 |
| test | 테스트 추가/수정 | test: Auth E2E 테스트 추가 |
| chore | 빌드, 설정 변경 | chore: TypeORM 설정 변경 |

## ⚠️ 자주 하는 실수

### 실수 1: synchronize: true를 프로덕션에서 사용
```typescript
// ❌ 프로덕션에서 절대 금지 (데이터 손실 위험)
TypeOrmModule.forRoot({
  synchronize: true,
})

// ✅ 환경별 분리
TypeOrmModule.forRoot({
  synchronize: process.env.NODE_ENV !== 'production',
})
```

### 실수 2: JWT Guard를 Global로 설정
```typescript
// ❌ Global Guard는 Public API도 막음
app.useGlobalGuards(new JwtAuthGuard());

// ✅ Controller별로 적용
@Controller('api/user')
@UseGuards(JwtAuthGuard)
export class UserController {}
```

### 실수 3: 비밀번호를 평문으로 비교
```typescript
// ❌ 절대 금지
if (password === user.password) {}

// ✅ bcrypt로 비교
const isValid = await bcrypt.compare(password, user.password);
```

### 실수 4: 환경변수를 직접 접근
```typescript
// ❌ 타입 불일치, undefined 가능성
const port = process.env.PORT;

// ✅ ConfigService로 타입 안전하게
const port = this.configService.get<number>('PORT') || 3000;
```

### 실수 5: Entity에서 synchronize 의존
```typescript
// ❌ synchronize에 의존하면 프로덕션에서 문제
// 새 필드 추가 → synchronize: false일 때 동작 안 함

// ✅ Migration 사용
npm run typeorm migration:generate -- -n AddSubscriptionFields
npm run typeorm migration:run
```

## 🚨 반드시 지켜야 할 규칙

### 절대 금지 (Never)
- ❌ Mock 데이터 사용
- ❌ 파일 무단 제거
- ❌ 직접 푸시 (커밋만 허용)
- ❌ synchronize: true (프로덕션)
- ❌ 평문 비밀번호 저장
- ❌ JWT_SECRET 하드코딩
- ❌ SQL Injection 취약점
- ❌ 임시 해결책

### 항상 수행 (Always)
- ✅ 실제 DB 테스트
- ✅ 근본 원인 해결
- ✅ 한글 커밋 메시지
- ✅ 환경변수로 비밀 관리
- ✅ bcrypt로 비밀번호 해싱
- ✅ ValidationPipe 사용
- ✅ 에러 로깅
- ✅ Co-Authored-By 태그
